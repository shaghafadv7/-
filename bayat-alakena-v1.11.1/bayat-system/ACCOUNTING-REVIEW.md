## 1) المعادلة الرسمية المعتمدة (مصدر الحقيقة الوحيد = قاعدة البيانات)

```
إجمالي المدفوع  = Σ(دفعات payments النشطة) + Σ(العربونات المربوطة بالصفقة)
المتبقي         = السعر الأساسي − Σ(الخصومات النشطة) ± Σ(التسويات المعتمدة) − إجمالي المدفوع
```

- تُحسب القيم داخل **Transactions** في Backend فقط، ولا تُعتمد حسابات JavaScript في الواجهة
  كمصدر نهائي (حسابات الواجهة للعرض المسبق فقط).
- كل عملية مالية تملك رقم قيد/مرجعًا فريدًا:
  - دفعة حجز: `RPY-سنة-رقم` — دفعة بيع: `PAY-سنة-رقم` — خصم: `DSC-...` — مصروف: `EXP-...`
  - تسوية: `ADJ-...` — عمولة: `CMP-...` — تصفية: `STX-...` — فاتورة: `INV-...`
- لا يُحذف أي سجل مالي صحيح حذفًا نهائيًا؛ الإلغاء يتم عبر `status='cancelled'` مع السبب والمستخدم
  والتاريخ، ويبقى الأثر في السجل المالي الكامل.

## 2) دورة الوحدة المختبرة (اختبارات آلية — `scripts/test-v1.9.js`)

```
متاحة → محجوزة → قيد عربون → تحويل الحجز لبيع → دفعات إضافية → تسوية
      → مسدد بالكامل → إعادة بيع → تصفية المالك السابق/المسوق
```

في كل مرحلة رُوجعت: حالة الوحدة، حالة الحجز، حالة البيع، مجموع الدفعات، المتبقي، الخصومات،
المصروفات، العمولة، الربح، مستحق المستثمر، التسويات، والسجل التاريخي.

## 3) نتائج فحص السلامة المالية (`GET /api/finance/integrity`)

| الفحص | النتيجة |
|---|---|
| `paid_amount` مطابق لجدول الدفعات + العربونات المربوطة | ✅ لا فروق |
| `final_price` مطابق لـ (الأساسي − الخصومات ± التسويات) | ✅ لا فروق |
| `remaining_amount` مطابق للمعادلة الرسمية | ✅ لا فروق |
| لا يوجد عربون نشط مرتبط برقم sale_id دون حالة نقل | ✅ لا فروق |
| لا يوجد حجز نشط مع بيع نشط على نفس الوحدة | ✅ لا فروق |

في الاختبار الشامل: فُحصت كل الصفقات المُنشأة خلال السيناريوهات — **صفر فروق**.

## 5) منع الأخطاء والتكرار المالي (قيود مفعلة)

| القيد | الآلية |

| نقل العربون إلى أكثر من بيع | فهرس فريد جزئي `one_rp_sale_link` + فحص قبل الربط |

| خصم أكبر من السعر | فحص Backend قبل الحفظ |

| تحويل بدون رقم مرجع | `validatePaymentMethod` — ترفض |

## 6) إصلاح محاسبي نُفّذ في v1.9

**المشكلة (كانت قائمة سابقًا):** الدفع الزائد فوق قيمة العقد كان يُدخل بالكامل في «الإيراد المحقق»
فيتضخم الربح رغم أنه رصيد دائن للعميل.

**الحل:** `realizedRevenue = min(paid, final)` — الإيراد المحقق لا يتجاوز قيمة العقد؛
الفرق الزائد يظهر كرصيد مستحق للعميل (`due_to_client`) ولا يدخل في الربح.
أثبتت الاختبارات: بعد دفع زائد 5,000 على صفقة قيمتها 590,000:
- الربح الإجمالي = 590,000 − 475,000 = **115,000** (وليس 120,000)
- صافي الربح = 115,000 − 25,000 مصروفات = **90,000** (وليس 95,000)
- نسبة صافي الربح = **18.95%** (وليس 20%)

## 7) حسابات مرتبطة أُعيد التحقق منها (اختبارات v1.8 التي كانت تفشل سابقًا → تنجح الآن)

- الخصم الثابت/النسبي والسعر النهائي.
- تكلفة الشراء وتحديثها ينعكس فورًا على الربح الإجمالي/الصافي والنسب.
- عمولة المسوق (مبلغ/نسبة) ودفعاتها وحالتها (جزئية/كاملة).
- صافي مستحق المستثمر في تصفية إعادة البيع.
- المالك السابق: المدفوع/المتبقي من صفقة الشراء الأولى يتحدث تلقائيًا.
- السجل المالي الكامل لكل صفقة (رصيد قبل/بعد كل حركة).

## 8) مطابقة الأرقام بين القنوات (اختبار 34)

- `GET /api/sales/:id/financial-summary` ← المصدر الموحد.
- تقرير المشاريع Excel: خلايا الصف نفسه (النهائي/العربون/المدفوع/المتبقي/رقم القيد) تطابق API تمامًا.
- سند البيع PDF: الأرقام (الأساسي 450,000 / العربون 5,000 / الدفعات 100,000 و 345,000) ورقم قيد
  الحجز `RPY-...` تظهر بنفس القيم.

## 9) نقاط لم تُغيّر عمدًا (حفاظًا على البيانات)

- لم تُربط العربونات القديمة المُرحّلة بصفقاتها التاريخية (لمنع تغيير أي رصيد سابق)؛
  سُجلت كقيود موثقة ويمكن ربطها يدويًا عبر التقرير.
- لم تُمسّ أي قيم مالية مخزنة للصفقات القائمة؛ كل الإصلاحات تُحسب لحظيًا من الجداول.

## 10) الخلاصة

بعد تشغيل الاختبارات فعليًا (v1.9: 101/101، وv1.8: 40/40 بعد الإصلاح):
- لا توجد فروق بين المدفوع المخزن ومجموع الدفعات، ولا بين المتبقي والمعادلة المحاسبية.
- لا تكرار للعربون ولا نقل لصفقة ثانية ولا ازدواج في القيود.
- الأرقام متطابقة في API والواجهة وPDF وExcel.
