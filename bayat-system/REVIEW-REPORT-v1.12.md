## 2) المشاكل التي أُصلحت

### المحرك المالي المركزي (المصدر الوحيد للحقيقة)
أُنشئ **`lib/finance.js`** ليكون المصدر الوحيد لكل رقم مالي:

```
السعر النهائي  = السعر الأساسي − الخصومات النشطة + صافي التسويات المعتمدة
إجمالي المدفوع = الدفعات المحصّلة فعليًا + العربون المربوط (مرة واحدة فقط)
المتبقي        = السعر النهائي − إجمالي المدفوع        (السالب = رصيد دائن للعميل)
الإيراد المحقق = min(المدفوع، السعر النهائي)            ← الدفع الزائد ليس إيرادًا
صافي الربح     = الإيراد المحقق − تكلفة العقار − العمولة − المصروفات
```

سياسة الحالات المالية طُبِّقت مركزيًا:
- `received` / `deposited` → تحصيل فعلي يدخل في المدفوع
- `pending` → **لا يدخل** في المدفوع، ويُعرض منفصلًا (`pending_amount`)
- `refunded` / `cancelled` وأي `status='cancelled'` → لا يدخل في أي حساب

كل هذه الجهات صارت تستدعي المحرك نفسه: لوحة التحكم، صفحة العميل، صفحة المشروع، صفحة الوحدة، الدفعات، التقارير، PDF، Excel.

### الإصلاحات المنفَّذة (مقابل الأرقام أعلاه)
1–7. حُذفت كل النسخ المحلية من الحساب واستُبدلت بالمحرك؛ حارس الدفع الزائد وتعديل البيع صارا يقرآن الحساب الحي شاملًا العربون؛ تقارير المبيعات/العمولات/العملاء تُحقن أرقامها من المحرك؛ التقرير المالي الشامل أُعيد بناؤه ببنود الإيرادات/المصروفات/العمولات (مستحقة + مدفوعة + متبقية)/الأرصدة (مستحقات + زائدة للعملاء + معلقة)/النتيجة (إجمالي + صافي)؛ الإجماليات الشهرية صارت تحترم حالة الدفعة وفلتر المشروع.

8–9. أُصلح عمود البنك في `UNION` (كان `NULL`)، وأُضيفت أعمدة `bank` / `check_due_date` / `check_status` / `updated_at` / `updated_by` لجدول `payments` وتُحفظ فعليًا.

10–11. السجل المالي صار يدعم الفلاتر المطلوبة كاملة وتعمل **معًا في آنٍ واحد**: المشروع + العميل + العقار + طريقة الدفع + البنك + الحساب المستلم + المستلم + الحالة + من/إلى تاريخ + من/إلى مبلغ + رقم المرجع + رقم العملية + النوع. وأُضيف شريط نتائج يعرض **عدد النتائج + إجمالي المبالغ + المحصّل + المعلّق + المرتجع + الملغى**، وزر **«إعادة تعيين الفلاتر»**.

12. تصدير PDF للدفعات صار يمرّر فلاتر الشاشة نفسها (`currentPaymentFilters()`)، وتقرير الدفعات في الخادم يقبل الفلاتر ذاتها ⇒ الشاشة = PDF = Excel.

13. شاشة الدفعات وُحّدت في شاشة واحدة، والجدول اختُصر إلى **الأعمدة المطلوبة فقط**: التاريخ، رقم العملية، العميل، المشروع، العقار، المبلغ، طريقة الدفع، المرجع، الحساب المستلم، الحالة — والتفاصيل الكاملة تظهر بالضغط على الصف.

14. الحقول صارت مرتبطة بطريقة الدفع (`data-pay-for`): تحويل → البنك + الحساب + المرجع • شيك → رقم الشيك + البنك + الاستحقاق + الحالة • نقدي → المستلم. الحقول المخفية تُفرَّغ حتى لا تُحفظ بيانات غير مرتبطة. وأُضيف وضع صارم اختياري (`strict_payment_fields`) لمنع حفظ عملية ناقصة محاسبيًا — **افتراضيًا مُطفأ حتى لا يمنع عمليات صحيحة**.

15–16. فاتورة البيع أُعيد ترتيبها إلى التسلسل المطلوب تمامًا (بيانات العميل ← العقار/المشروع ← قيمة العقار ← الخصومات ← السعر النهائي ← إجمالي المدفوع ← المتبقي ← عمولة المسوق ← المصروفات ← تفاصيل الدفعات ← التذييل)، والعربون ودفعات البيع دُمجا في **جدول واحد بإجمالي واحد**.
النتيجة المقيسة على نفس الفاتورة:

| الرقم | قبل | بعد |
|-------|-----|-----|
| 1,250,000 | 4 مرات | **1** |
| 1,200,000 | 4 مرات | **1** |
| 950,000 (المتبقي) | 6 مرات | **1** |
| 250,000 (المدفوع) | 10 مرات | 4 (مرة في الملخص + سطر الدفعة + إجمالي) |
| عدد الصفحات | 5 | **4** |

17. أُضيف **`/api/reports/project-account`**: ملخص إداري أعلى التقرير (عدد الوحدات، المباع، المحجوز، المتاح، قيمة المبيعات، التحصيل، المتبقي، المصروفات، العمولات، صافي الربح) ثم جدول العمليات — بلا تفاصيل داخلية في الصدارة.

18–19. كل أرقام العمليات تُولَّد الآن عبر `uniqueNo()` مع فحص التفرد، وأُضيف `assertUniqueRef()` الذي يمنع تكرار رقم الشيك/الحوالة على نفس البنك عبر جدولي الدفعات ودفعات الحجز.

20. فحص السلامة أُعيد بناؤه ليغطي: المدفوع، المتبقي، النهائي، الخصومات، التسويات، العمولات (وتجاوز المدفوع للمستحق)، المصروفات، الربح، رصيد العميل، الدفعات المعلقة، العربون غير المربوط، عربونات من حجوزات متعددة، بيعان/حجزان نشطان لنفس الوحدة، الحجز النشط على وحدة مباعة، والأرقام المرجعية المكررة. وكل خلل يعرض: **رقم الصفقة + الرقم المرجعي + المشكلة + القيمة الحالية + القيمة الصحيحة + السبب**، مع تمييز `severity:'info'` لما ليس خطأً (رصيد دائن/دفعات معلقة). وأُضيف `POST /api/finance/integrity/repair` الذي يعيد الاحتساب من المحرك **دون المساس بأي قيد مالي** ويوثّق ما صحّحه.

21. أُضيفت 13 فهرسًا على الأعمدة الأكثر استخدامًا، واستعلامات المحرك مُعدّة مسبقًا (prepared) مرة واحدة.

22. أُصلح التمرير: سقف ارتفاع للجداول مع **رؤوس أعمدة ثابتة**، أشرطة تمرير ظاهرة دائمًا، مساحة أمان أسفل الصفحة (60px) وأسفل القائمة الجانبية (26px) — يعالج تحديدًا مشكلة الوصول لأسفل الصفحة/القائمة على Windows Desktop.

## 4) التغييرات في قاعدة البيانات

كلها **إضافية وغير هدّامة** (`ensureColumns` / `CREATE INDEX IF NOT EXISTS`)، تُطبَّق تلقائيًا عند الإقلاع:

- **أعمدة جديدة على `payments`**: `bank`, `check_due_date`, `check_status`, `updated_at`, `updated_by`
- **إعداد جديد**: `strict_payment_fields = '0'`
- **13 فهرسًا جديدًا** على: `payments(sale_id,status,payment_status)`, `payments(pay_date)`, `reservation_payments(sale_id,…)`, `reservation_payments(reservation_id,status)`, `reservation_payments(pay_date)`, `discounts(sale_id,status)`, `expenses(sale_id,status)`, `commission_payments(sale_id,status)`, `financial_adjustments(sale_id,status,type)`, `sales(customer_id,status)`, `sales(unit_id,status)`, `sales(sale_date)`, `units(project_id,status)`
- **فهرس تفرد**: `reservation_payments(payment_no)`

**لا حذف لأي جدول أو عمود أو صف. لا تعديل لأي قيمة مالية تاريخية.** الأعمدة المخزَّنة في `sales` تُحدَّث فقط لتطابق ما يحسبه المحرك، وهو ما كان يفترض أن تكون عليه أصلًا.

## 6) الجولة الثانية — استكمال البنود المؤجلة

نُفِّذت البنود التي كانت مؤجلة في التقرير الأول:

| البند | ما نُفِّذ |
|------|---------|
| **13 — صفحة العميل** | كشف الحساب صار بالتسلسل المطلوب: العميل ← عدد العقارات ← إجمالي قيمة العقود ← إجمالي المدفوع ← إجمالي المتبقي ← ثم جدول العقارات. وكل عقار يعرض (قيمة العقد، الخصم، السعر النهائي، المدفوع، المتبقي، العمولة، المصروفات) في صف واحد قابل للنقر يفتح الدفعات — بلا تكرار للأرقام |
| **7 — فلاتر حساب العميل** | أُضيفت كاملة: العميل + المشروع + العقار + حالة الصفقة + الفترة + حالة السداد، تعمل معًا، مع زر إعادة تعيين وشريط يعرض عدد النتائج والإجماليات |
| **14 — صفحة المشروع** | زر «حساب المشروع» على كل بطاقة يفتح ملخصًا سريعًا (عدد الوحدات، المباع، المحجوز، المتاح، قيمة المبيعات، التحصيل، المتبقي، المصروفات، العمولات، صافي الربح) ثم جدول العمليات |
| **15 — القائمة الجانبية** | دُمج عنصرا «تصفيات المستثمرين» و«تصفية المسوقين» في عنصر واحد «التصفيات» بتبويبين (19 عنصرًا بدل 20)، مع إبقاء المسار القديم يعمل للتوافق |
| **الوضع الصارم** | صار قابلًا للتفعيل من واجهة الإعدادات مباشرة، ومحميًا بصلاحية «إدارة إعدادات النظام» في الخادم (لا يكفي إخفاء الحقل) |
| **حالة «دفع زائد»** | أُضيفت كحالة سداد معروضة بلون مميز في الجداول والفلاتر |

### ما تبقّى (بقرار واعٍ لا إهمال)
1. **شاشات المخزون** (الوحدات، النماذج والأدوار، أرشيف المستندات): تعمل بشكل سليم وتفتح بلا أخطاء (مثبت في فحص الواجهة). لم أغيّرها لأن أي تعديل فيها لا يحقق أحد أهدافك الستة — وقاعدتك رقم 24 تمنع التغيير لمجرد التغيير.
2. **تأكيد بصري على Windows Desktop**: إصلاحات التمرير مطبقة في CSS (سقف ارتفاع + رؤوس أعمدة ثابتة + أشرطة مفروضة الظهور + مساحات أمان أسفل الصفحة والقائمة). لا تتوفر لي بيئة ويندوز للتأكيد البصري النهائي — تحتاج نظرة منك.
